# Quantitative research pipeline for NASDAQ hypothesis testing

A complete greenfield framework that generates 103 market-behavior hypotheses from daily OHLCV data, applies Benjamini-Hochberg FDR correction, runs walk-forward and out-of-sample validation, models transaction costs, designs entry/exit rules with half-Kelly sizing, and produces a markdown report. The multi-stage rejection funnel correctly addresses multiple-comparisons inflation, in-sample overfitting, regime fragility, and cost erosion.

Watch for: ORDER_FLOW_PROXY hypotheses bypass rejection criteria even when they fail all statistical thresholds (confirmed); the pipeline feeds `train_data` (60% split) into strategy design while validation used `full_data`, creating a data-leakage asymmetry (confirmed); Kelly criterion inputs are derived from unreliable backtest proxies that conflate drawdown with average loss (confirmed); broad `except Exception` swallowing throughout the orchestrator makes production failures invisible (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The ORDER_FLOW_PROXY exemption in the rejection logic introduces a category of hypotheses that survive despite failing every statistical threshold. These flow through the full pipeline — walk-forward, OOS, strategy design — even though they were flagged as statistically insignificant. The exemption should either be removed or these hypotheses should be excluded from downstream capital allocation.

The orchestrator uses `train_data` (the first 60%) as the optimization dataset for strategy design, but calls `backtest_rules` on `full_data` — meaning the OOS holdout data that validated the hypothesis is then used again in the entry/exit backtest. Separately, both walk-forward and OOS validators receive the same `full_data`, and the walk-forward expanding window's final fold extends into what OOS treats as holdout.

Transaction cost modeling is comprehensive (commission, spread by vol regime, square-root market impact, volume-dependent slippage), but the pipeline applies costs to raw 1-day signal returns rather than to the actual strategy's multi-bar trade stream with ATR-based stops and holding periods. The "survives costs" gate is measuring a different strategy than what gets deployed.

Test coverage is strong for individual modules (129 tests pass) but does not exercise the ORDER_FLOW_PROXY bypass path end-to-end, and no test verifies that the data splits used in strategy optimization are disjoint from validation holdouts.

<summary>Issues (6)</summary>

1. **ORDER_FLOW_PROXY bypass** — Hypotheses in this category are un-rejected even when they fail all three statistical criteria. Remove the bypass or prevent these hypotheses from receiving capital allocation downstream.
2. **Train/holdout data leakage in strategy design** — `EntryExitDesigner.design_rules` is called with `train_data` (first 60%), but `backtest_rules` is called with `full_data`, which includes the OOS holdout. Backtest the strategy only on data disjoint from both validation holdout and optimization.
3. **Kelly criterion input mismatch** — `max_drawdown` is used as `avg_loss` in the Kelly formula; drawdown is a path-dependent statistic, not an average per-trade loss. Use the actual average losing-trade magnitude from `backtest_metrics`.
4. **Silent exception swallowing** — Every pipeline step catches `Exception` and logs an error but continues. In a research pipeline this means a broken signal function produces an empty result that is indistinguishable from "no edge." Add explicit status tracking or fail loudly on unexpected errors.
5. **Transaction cost model applied to raw signal returns, not strategy trades** — `TransactionCostModel.evaluate` computes costs from `compute_signal_returns` (forward 1-day returns on signal days), while the actual strategy uses ATR-based stops and holding periods. Costs should be applied to the strategy's trade stream.
6. **Validation pipeline uses full data for both WF and OOS** — Both `WalkForwardValidator` and `OutOfSampleValidator` receive the same `full_data` DataFrame. The walk-forward validator's expanding window may overlap the OOS holdout, contaminating the OOS test.

## ORDER_FLOW_PROXY rejection bypass

In `rejection.py` lines 223–230, when a hypothesis belongs to the `ORDER_FLOW_PROXY` category and has been rejected by one or more criteria, the code sets `rejected = False` and relabels it as `limited_data_confidence`. This means a hypothesis with p-value 0.95, Sharpe -0.5, and 10 observations still survives into the validation pipeline and — if it passes walk-forward on noise alone — can reach capital allocation.

```python
if hyp.category == HypothesisCategory.ORDER_FLOW_PROXY:
    if rejected:
        confidence_flag = "limited_data_confidence"
        ...
        rejected = False  # <-- bypasses all three rejection criteria
```

The fix is either to reject these hypotheses normally and annotate the report with their data-limitation flag, or to impose a separate (perhaps more lenient) threshold set for this category rather than exempting them entirely.

## Train/holdout contamination in strategy design

The main orchestrator splits data into train (60%), validation (20%), holdout (20%) at the top of `run_pipeline`. The validation pipeline receives `full_data` and internally extracts its own holdout (the last 20–25%). Strategy design then calls:

```python
rules = designer.design_rules(hyp, train_data)        # optimize on 60%
bt_result = designer.backtest_rules(rules, hyp, full_data)  # backtest on 100%
```

The backtest on `full_data` includes both the validation walk-forward folds and the OOS holdout. The resulting `backtest_metrics` therefore reflect performance on data that was already used to validate the hypothesis. A correct setup would backtest only on `train_data` (for in-sample metrics) or on a fresh holdout that was not touched by the validation pipeline.

## Kelly criterion with drawdown as loss input

In `main.py` step 9:

```python
avg_win = max(metrics.get("expectancy", 0.001), 0.001)
avg_loss = max(abs(metrics.get("max_drawdown", 0.01)), 0.001)
position_size = sizer.kelly_criterion(
    win_rate=hit_rate, avg_win=avg_win, avg_loss=avg_loss, half_kelly=True,
)
```

`expectancy` is the mean return per trade (not average win — it includes losses). `max_drawdown` is the worst peak-to-trough path decline, not the average losing trade. Kelly requires the average win magnitude and average loss magnitude on a per-bet basis. Using drawdown here will systematically over-size positions when drawdown is small and under-size when drawdown is large, decoupling the position sizing from actual trade-level risk.

## Silent exception handling in the orchestrator

Some steps `return result` (aborting the pipeline) while others silently continue. Step 7 (validation) catches and continues, so if the entire validation pipeline throws, the pipeline proceeds to strategy design with `validated_survivors = []` and silently produces an empty report — correct output but for the wrong reason. If a single signal function raises inside the validation loop, it's caught inside `StatisticalTester.compute_signal_returns` (which also catches generically), returning an empty Series that the downstream logic treats as "no edge" rather than "error." A broken hypothesis becomes indistinguishable from a hypothesis with no predictive power.

## Transaction cost model misalignment

`TransactionCostModel.evaluate` computes gross returns via `compute_signal_returns` — which returns 1-day forward returns weighted by signal direction. But the actual strategy in `entries_exits.py` holds positions for multiple bars with stop-losses, trailing stops, and time-based exits. The cost model applies costs on every signal change (which fires daily for many signals), dramatically overstating turnover compared to the actual strategy which only trades on entry/exit events.

A hypothesis might fail cost analysis because its daily signal flips frequently, even though the actual strategy (with confirmation bars and holding periods) trades infrequently. Conversely, a hypothesis with a stable daily signal might pass cost analysis but generate many trades due to stop-loss exits that the cost model never sees.

## Walk-forward / OOS data overlap

Both validators receive the entire `full_data` DataFrame in `ValidationPipeline.run`. The walk-forward validator uses expanding windows that grow to cover the full dataset. The OOS validator splits the last 25% as holdout. The walk-forward expanding window's final fold extends into what OOS treats as unseen holdout, inflating apparent consistency.

The pipeline should either pass only the non-holdout portion to walk-forward, or call `OOS.split_holdout` first and pass only the development portion to walk-forward.

## Test coverage gaps

- No test exercises the ORDER_FLOW_PROXY bypass path end-to-end to verify these hypotheses are correctly flagged in the report.
- No test verifies data-split disjointness between validation and strategy optimization.
- Signal functions in `signals.py` (1312 lines, 103 functions) have no dedicated unit tests — they are tested only indirectly through the hypothesis/validation tests using synthetic data. A single signal that returns the wrong shape or raises on edge-case inputs would only be caught at integration time.
