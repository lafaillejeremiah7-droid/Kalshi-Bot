The six issues raised in the first review have all been addressed correctly: ORDER_FLOW_PROXY hypotheses are now rejected normally (with a `limited_data_confidence` annotation), strategy backtesting uses `train_data` exclusively, Kelly criterion pulls `avg_win`/`avg_loss` from the metrics dictionary, exceptions propagate via `raise`, transaction costs operate on discretized position changes, and walk-forward receives only the non-holdout portion of data. Watch for: Kelly criterion inputs (`avg_win`, `avg_loss`, `hit_rate`) are derived from daily active returns rather than per-trade PnL, which biases sizing for multi-bar trades (confirmed); the `wf_data` parameter path is untested, meaning a regression could silently reintroduce WF/OOS overlap (likely).

**Verdict**: APPROVED

## High-level view

Position sizing uses daily-return-level statistics where per-trade statistics are required. The backtest simulation produces a `trades` list with per-trade PnL, but `_compute_metrics` ignores it and instead computes `avg_win`/`avg_loss`/`hit_rate` from the daily returns series. A winning trade held for 10 bars contributes 10 data points to the win statistics, biasing hit rate upward and distorting average magnitudes. This is a correctness gap, not a safety gap — the half-Kelly cap at 20% and the risk controller provide layered protection — but it means the Kelly fraction is derived from the wrong distribution.

The `wf_data` parameter in `ValidationPipeline.run` is the mechanism that prevents WF/OOS overlap, but no test exercises it. If this parameter were accidentally removed or defaulted to `data`, the overlap would return silently. A single integration test asserting that WF folds don't extend into the OOS holdout would lock in the fix.

## Kelly criterion operates on daily returns, not trade returns

The backtest in `entries_exits.py` produces both a `trades` list (with per-trade `pnl`, `bars_held`, `entry_price`, `exit_price`) and a `daily_returns` Series. The `_compute_metrics` method computes all statistics from `active_returns = returns[returns != 0]` — the daily returns on days a position is held:

```python
active_returns = returns[returns != 0]
hit_rate = self.tester.compute_hit_rate(active_returns)  # fraction of positive DAYS
winning_trades = active_returns[active_returns > 0]
avg_win = float(winning_trades.mean())  # average winning DAY
```

The Kelly criterion is defined over independent bets. A single trade spanning 5 bars contributes 5 observations to `active_returns`, making consecutive daily returns within one trade non-independent. The practical effect: a winning trade held 10 days counts as 10 wins, while a stop-loss exit after 2 days counts as 2 losses. Hit rate is inflated for strategies with long holding periods on winners and short holding periods on losers (exactly what ATR-based trailing stops produce).

The `trades` list already contains per-trade `pnl`. A trade-level computation would look like:

```python
trade_pnls = [t["pnl"] for t in trades]
winning = [p for p in trade_pnls if p > 0]
losing = [p for p in trade_pnls if p < 0]
hit_rate = len(winning) / len(trade_pnls)
avg_win = np.mean(winning) if winning else 0.0
avg_loss = np.mean([abs(p) for p in losing]) if losing else 0.0
```

The severity is moderate because the 20% max position cap and the half-Kelly multiplier provide conservative guardrails that limit the practical impact of biased estimates.

## WF/OOS disjointness is unverified by tests

The fix to pass `wf_data` (first 75%) to the walk-forward stage while reserving the last 25% for OOS is correct in the current code. However, neither the integration tests in `test_main.py` nor the pipeline tests in `test_validation.py` exercise the `wf_data` parameter path. All existing pipeline tests call `pipeline.run(hypotheses, data)` without `wf_data`, which causes the fallback to `wf_data = data` (the old behavior). A test like:

```python
def test_wf_data_excludes_oos_holdout():
    pipeline = ValidationPipeline(...)
    wf_data = full_data.iloc[:int(len(full_data) * 0.75)]
    report = pipeline.run(hypotheses, full_data, wf_data=wf_data)
    # Assert fold boundaries don't exceed wf_data's end date
    for wf_result in report.walk_forward_results:
        for fold in wf_result.fold_results:
            assert fold.test_end <= str(wf_data.index[-1].date())
```

would prevent regression.
